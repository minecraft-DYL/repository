# Wyolm — 别住在我的 C 盘上

一个 .NET + WinUI 3 的 Windows 桌面工具，专门解决一件事：

**把 C 盘上占地的大文件夹搬到别的盘，然后在原位置留下一个目录联接，让所有程序以为它还在原地。**

以及反过来：**扫描任意盘符，把搬走的文件夹用链接接回 C 盘原位置。**

> 名字来自仓库作者每次看到 `C:\Users\me\.nuget` 涨到 20 个 G 时的真实心声。

## 它保证什么

| 承诺 | 怎么做到的 |
|---|---|
| **失败了自动回滚，原文件夹不会有事** | 复制 → 校验 → 建链接，每一步都有明确的回滚动作；只有"目标副本校验通过 + 链接确认可用"之后才会去删原盘的旧数据 |
| **数据搬过去之后真的是同一份** | 三档校验可选，最强一档对每个文件算 SHA-256 全量哈希 |
| **不会顺着链接把别的盘清空** | 删除逻辑遇到重解析点只删链接本身，绝不递归进去（有专门的测试钉住这条性质） |
| **不会让你把系统盘搬走** | 路径守卫硬性拦截 `C:\`、`C:\Windows`、`AppData`、用户目录本身等关键位置 |
| **不需要管理员权限** | 默认使用目录联接（Junction），免管理员也免开发者模式 |
| **长路径不会中途失败** | 应用声明 `longPathAware`，可以处理超过 260 字符的路径（`node_modules`、`pip` 缓存很容易超） |
| **半路断电/蓝屏也能收拾干净** | 每一步动作之前先把意图写进事务日志，下次启动时自动判断该收尾还是该回滚 |

## 三个主要功能

### 1. 扫描与搬家

选定一个盘或目录 → 扫描第一层文件夹的实际占用体积 → 勾选要搬走的 → 选目标盘 → 执行。

列表会把 `.nuget`、`.gradle`、`node_modules`、`AppData\Local\JetBrains` 这类"体积大户"标出来，省得自己猜。

### 2. 接回原位

这是"扫描自定义盘符然后用符号链接连上原来文件夹"那条需求。

* 每次搬家/复制都会在目标文件夹里写一个 `.wyolm-origin.json` 标记，记录它原本住在哪。
* 「接回原位」页可以扫描**任意盘符的任意深度**，凭这些标记把可接回的文件夹列出来，一键把链接接回原位置。
* 对于你自己手动搬过去的文件夹（没有标记），页面下方提供**手动接回**：填"真实位置"和"原位置"，直接建链接。

### 3. 自定义迁移

任意文件夹 → 任意位置，三种模式：

| 模式 | 做什么 | 数据安全边界 |
|---|---|---|
| **搬家 + 原位建链接** | 复制 → 校验 → 原位置建链接 → 删原盘旧数据 | 校验通过且链接可用之前，原目录不动 |
| **只复制** | 复制到目标，原文件夹保留 | 校验失败就删掉副本 |
| **只建链接** | 不搬数据，只在原位置建链接指向已存在的位置 | 失败只拆链接，绝不碰真实数据 |

选项：链接类型（联接 / 符号链接）、校验强度、试运行、允许合并进已有目录、跳过占用检查、**成功后保留原盘旧数据**（谨慎模式，给自己留后路）。

## 它怎么保证不把你的电脑搞坏

### 硬性拦截的路径

```
C:\                      C:\Windows               C:\Program Files
C:\Program Files (x86)   C:\ProgramData           C:\Users
C:\Boot                  C:\Recovery              C:\System Volume Information
C:\$Recycle.Bin          C:\PerfLogs              C:\MSOCache
...\AppData              ...\AppData\Local        ...\AppData\Roaming
...\AppData\Local\Temp   C:\Users\<你>（用户目录本身）
```

另外还会拒绝：盘符根目录、正在运行的 Wyolm 自己所在的目录、目标位于源内部、源位于目标内部、目标已被非空占用（除非勾选合并）。

`桌面 / 文档 / 下载 / 图片` 这类 Windows 已知文件夹只给**警告**不拦截 —— 很多人确实想搬 Downloads，但如果有程序硬编码了路径就可能出问题，所以提醒你自己判断。

### 三层删除安全

1. **回滚边界**：链接确认可用之后，不再回滚。因为此时目标副本已校验、链接已生效，再回滚只会把一份残缺数据搬回来。
2. **合并模式保护**：如果目标目录是合并进去的（原本就有你的文件），回滚只删 Wyolm 自己写进去的那些文件，绝不整目录删。
3. **链接不跟随**：递归删除遇到目录联接/符号链接时，只删链接本身。这是"清理 C 盘旧数据"不会变成"清空 D 盘"的原因，有专门的测试守着。

## 搬家的完整流程

```
① 前置检查         路径合法性、剩余空间、文件占用探测
   │  不通过 → 直接拒绝，一个字节都不动
   ▼
② 清点             枚举出完整清单（文件数、总大小、时间戳、嵌套链接）
   ▼
③ 复制             源 → 目标
   │  失败 → 删掉复制了一半的目标，原目录完好      ← 回滚点
   ▼
④ 校验             结构 / 大小+时间戳 / SHA-256 全量哈希
   │  失败 → 删掉目标副本，原目录完好              ← 回滚点
   ▼
⑤ 写来源标记       在目标里写入 .wyolm-origin.json
   ▼
⑥ 腾出原位置       源目录改名为同盘的临时备份目录（文件系统原语，瞬间完成）
   ▼
⑦ 建立链接         在原位置创建目录联接
   │  失败 → 备份改回原名，删目标副本，完全还原    ← 回滚点
   ▼
⑧ 确认链接可用     透过链接真实地读一次，确认指向正确、内容可见
   │  失败 → 同上，完全还原                        ← 回滚点
   ▼
   ⛔ ────────── 回滚边界 ────────── ⛔
   ▼
⑨ 清理旧数据       删除临时备份目录（数据在这一步真正离开原盘）
   │  失败 → 只是留下一个可以手动删的目录，功能不受影响
   ▼
⑩ 完成
```

## 崩溃也能恢复

每个作业的每一步都写在 `%LOCALAPPDATA%\Wyolm\journal\<作业ID>.json` 里，**先写日志再动手**。

应用每次启动时会读这些日志，结合磁盘上的实际状态判断：

| 中断的位置 | 恢复动作 |
|---|---|
| 复制 / 校验阶段 | 删掉目标上的半成品，源目录本就没动 |
| 已改名、链接还没建好 | 备份改回原名，删掉目标副本 —— 完全还原 |
| 链接已建好 | **收尾**：删掉残留的备份（回滚反而会破坏一份已生效的数据） |
| 合并模式中断 | **不自动处理**，标记为需人工确认 —— 宁可留一份多余数据，也不误删你的文件 |
| 只建链接模式中断 | 最多拆掉一个没建好的链接，绝不碰真实数据 |

启动时会弹窗告知，也可以随时在「历史与恢复」页查看。

## 构建与运行

### 环境要求

**运行**（用户侧）：

* Windows 10 1809 (17763) 或更高
* 什么都不用装。

应用把 Windows App SDK 运行时 **和** .NET 运行时都打进了自己的目录（`WindowsAppSDKSelfContained` + `SelfContained`），双击 exe 就能用。这不是洁癖，是被现实教育出来的：这台机器上装着 1.8 的运行时，但版本（`8000.946.1701.0`）低于 SDK 期望的 `8000.994.2142.0`，程序会直接弹出「Required components of the Windows App Runtime are missing」拒绝启动。要求用户先去装一个运行时，对一个"帮你清 C 盘"的小工具来说完全不可接受。

**构建**（开发侧）：

* .NET SDK 8.0 或更高（已在 .NET 10 SDK + `net10.0-windows10.0.19041.0` 上验证）
* 首次构建需要联网还原 NuGet 包

### 构建

整个解决方案：

```powershell
dotnet build WhyAreYouLivingOnMyCDrive.slnx -c Debug
```

或者只构建界面程序（指定 x64 平台）：

```powershell
dotnet build src\Wyolm.App\Wyolm.App.csproj -c Debug -p:Platform=x64
```

> ⚠️ 不要给**解决方案**传 `-p:Platform=x64` —— `.slnx` 里只声明了默认平台，传了会因为「无效的解决方案配置 Debug|x64」直接报 MSB4126。构建单个 csproj 时才需要 `-p:Platform=x64`。

两条路产出的 exe 都可**直接双击运行**（已实测）：

```
src\Wyolm.App\bin\Debug\net10.0-windows10.0.19041.0\win-x64\Wyolm.App.exe        # 解决方案构建
src\Wyolm.App\bin\x64\Debug\net10.0-windows10.0.19041.0\win-x64\Wyolm.App.exe    # 指定平台构建
```

### 运行（开发时）

```powershell
dotnet run --project src\Wyolm.App\Wyolm.App.csproj -p:Platform=x64
```

### 发布

```powershell
dotnet publish src\Wyolm.App\Wyolm.App.csproj -c Release -p:Platform=x64
```

`WindowsAppSDKSelfContained` 和 `SelfContained` 已经写进 csproj，不需要额外传参。产物在：

```
src\Wyolm.App\bin\Release\net10.0-windows10.0.19041.0\win-x64\publish\
```

> 注意路径里**没有 `x64` 这一段** —— WinUI 的 `win-x64.pubxml` 发布配置自己指定了 `PublishDir`，和 `Platform` 无关。

实测产物约 **130.8 MB / 339 个文件**（自带 .NET 运行时 + Windows App SDK 的代价）。把 `publish\` 整个目录拷到别的机器上，双击 `Wyolm.App.exe` 就能跑 —— 目标机器 **不需要** 装 .NET 运行时，也不需要装 Windows App Runtime。

## 常见问题

**为什么默认用"目录联接"而不是"符号链接"？**

目录联接创建**不需要管理员权限也不需要开发者模式**，覆盖 `C:\Users\...` 这种同机路径的场景完全够用。符号链接的语义更"正统"、能做相对路径，但通常需要权限 —— 界面上两个都提供，如果探测到当前环境建不了符号链接，前置检查会提前拦住。

**搬迁之后程序还能正常用吗？**

绝大多数情况可以 —— 目录联接对应用程序是透明的。极少数程序会检测"这个目录是不是链接"或对路径做了特殊处理，可能表现异常。所以：

* 「桌面/文档/下载」这类已知文件夹只给警告；
* 提供「完成后保留原盘旧数据」，确认一切正常后再手动清理；
* 出问题随时可以把链接拆掉、把数据搬回来。

**搬完 C 盘怎么没变大？**

检查「完成后」那个开关 —— 如果开着「保留原盘旧数据」，旧数据会留在原盘上（这是刻意设计的谨慎模式）。确认没问题后手动删掉备份目录即可，历史记录里会写它在哪里。

**搬走之后想在别的机器上找回原位怎么办？**

目标文件夹里带着 `.wyolm-origin.json`，记录着它原本住在哪。在新机器上用「接回原位」扫描那个盘就能找出来。

**迁移失败并且"回滚未完成"怎么办？**

**先不要删除任何文件。** 日志在 `%LOCALAPPDATA%\Wyolm\logs\`，历史记录和恢复报告里会写明是哪个路径、卡在哪一步。这种状态意味着磁盘状态需要人工确认，工具刻意选择了"停下来报告"而不是"继续猜着修"。

**双击 exe 弹出「This application could not be started」，或者窗口一闪就没了？**

看 `%LOCALAPPDATA%\Wyolm\logs\crash.log`。

* 如果提示 **Windows App Runtime 缺失或版本过低** —— 说明这个 exe 是老的、非自带运行时的构建。重新用当前 csproj 构建即可，它已经把运行时打进输出目录了。
* 如果日志里是某个页面构造时的异常 —— 这是真实的 bug，请把 `crash.log` 那一段贴出来。应用现在会**兜住导航失败**：某一个页面打不开时会弹提示，另外三个页面仍然可用，不会再整个程序闪退。

**为什么应用数据放在 `%LOCALAPPDATA%\Wyolm`？**

事务日志、历史记录、运行日志都放那儿。可以直接在「历史与恢复」页点「打开数据目录」或「打开日志文件夹」跳过去。数据根目录是可覆盖的（`AppPaths.DataRoot`），将来做便携模式就用这个口子。
